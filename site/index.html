Test your n8n workflows before your client does.

Breaker runs a disposable copy of your workflow against the cases you declare, reads the results back on its own, cleans up, and tells you exactly what was proven and what was not.

Your real workflows and Data Tables are never written. Anything Breaker can't run safely, it refuses before creating anything.

  • Apache-2.0
  • Python, stdlib only
  • local n8n only
  • 602 offline tests

What Breaker does

    What it checks, and what it refuses

    Most broken workflows were only ever tested on the happy path. Breaker makes the other paths runnable, without risking the instance you depend on.

    1. 01

      You declare the cases

      Inputs, the nodes that must run, the output each node must produce, and the rows a Data Table must hold afterwards. Optionally, the business requirements each case proves.

    2. 02

      It runs a disposable copy, never your workflow

      Outbound nodes are replaced by stubs, Data Tables by fresh disposable tables seeded per case. Every create is journalled and deleted by id after the run; a before/after snapshot of the whole instance must match.

    3. 03

      It refuses rather than guesses

      Code nodes, unsupported Data Table operations, a workflow that changed since its requirements were written, a different n8n build than the one probed: all stop the run before anything is created. Results never say "verified"; untested promises are labelled as such.

    How to use it

    Three steps. Step 1 never touches n8n. Steps 2 and 3 talk only to an n8n running on your own machine, and only after you arm them for that exact run.

    1. 1

      Check your workflow offline

      Export the workflow, write a cases file (see fixtures/requirements/lead-intake/), and let Breaker tell you whether it can test it and what it would need.

      Commands
      git clone REPO_URL breaker && cd breaker
export PYTHONPATH=src
python tools/breaker_verify_workflow.py fixtures/requirements/lead-intake/workflow.json \
  --cases fixtures/requirements/lead-intake/cases.json \
  --requirements fixtures/requirements/lead-intake/requirements.json \
  --out-root "$PWD/../scratch-breaker" --label first-look
    2. 2

      Prove the mechanism on your local n8n, once

      Two small probes confirm that stubbing and disposable Data Tables behave on your n8n build. Each creates one throwaway workflow, runs it, and deletes it. Keep the records they write.

      Commands
      export N8N_BASE_URL=http://127.0.0.1:5678
# set N8N_API_KEY and MCP_N8N_API_KEY yourself; never paste them anywhere
export BREAKER_S4_APPROVAL="gate1:http://127.0.0.1:5678:p1"
python tools/breaker_s4_run.py probe --base-url http://127.0.0.1:5678 \
  --out-root "$PWD/../scratch-breaker" --run-label p1
export BREAKER_S4_APPROVAL="tableprobe:http://127.0.0.1:5678:tp1"
python tools/breaker_table_probe.py --base-url http://127.0.0.1:5678 \
  --out-root "$PWD/../scratch-breaker" --label tp1
    3. 3

      Run your cases

      Arm the run, point it at the two probe records and the n8n version you expect. Breaker checks the instance first, runs each case in its own reset table, reads the rows back, deletes what it made, and writes the report.

      Commands
      export BREAKER_S4_APPROVAL="run:http://127.0.0.1:5678:r1"
python tools/breaker_verify_workflow.py my-workflow.json --cases my-cases.json \
  --requirements my-requirements.json --out-root "$PWD/../scratch-breaker" --label r1 \
  --run --base-url http://127.0.0.1:5678 \
  --mechanism-record ../scratch-breaker/p1/<probe-dir>/mechanism-record.json \
  --table-mechanism-record ../scratch-breaker/tp1/<probe-dir>/table-mechanism-record.json \
  --expect-n8n-version 2.35.4

    Built in public

    The honest version of how this got here, including the run that did not go through.

    1. Stable 1

      One front door for any workflow

      Generic preflight, neutraliser and runner. Every real step disarmed until the operator arms it for one run.

    2. Data Tables

      Disposable tables, reset per case

      A real probe proved get, insert and upsert on a throwaway table; the first end-to-end run read rows back exactly as declared.

    3. Requirements

      Coverage you can't over-read

      Requirements are bound to the exact workflow file. No status says "verified"; unproven promises are labelled.

    4. Test safety

      The test suite can't touch your instance

      An offline guard blocks network, Docker and subprocess calls during tests and fails the run if anything tries.

    5. Run comb1

      Refused before creating anything

      n8n did not expose its version to Breaker, so the new version check stopped the run. Nothing was created. That is the tool working.

    6. Run comb2

      CONFORMS on a real instance

      2 executions, 1 disposable workflow and 1 table created and deleted, the instance unchanged afterwards. The version was taken from operator evidence and labelled as not verified.

    7. Stable 2

      Frozen and released

      Release gate: 2735 internal tests passed. Open-source build: 602 tests, zero dependencies.

    What it won't do (yet)

    Said up front, so nothing is a surprise later.

    • Run Code nodesThey are blocked until their execution can be isolated.
    • Test your real integrationsEmail, CRM and API side effects are stubbed; promises about them are reported as needing a human or a real integration test.
    • Certify production readinessEvery run is simulated evidence from a disposable copy. The report says so.
    • Every Data Table operationNode v1.1 with a static table and get, insert or upsert. Others are refused.
    • Hosted or remote n8nOnly an instance on your own machine (loopback).
    • Verify a hidden n8n versionIf your instance hides it, you supply container evidence and the report marks it unverified.
